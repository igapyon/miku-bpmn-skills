# P0002-00000 — miku-bpmn の GitHub Release

この親 Process は、[P00002 の作業記録と根拠表](../../process-mining/P00002/README.md)から組み立てた例です。

## 目的と入力

版数付きの変更を GitHub Release として公開し、PR のマージ後に次の作業ブランチを開始します。親 Process は対象リポジトリ、作業ブランチ、既存の変更とその目的、版数の更新指定と規約、配布 ZIP のビルド手順、リモート、base ブランチ、GitHub 上でレビューと公開を行う担当者を受け取ります。各操作を始めるときに必要な利用者の依頼は、下の表に示します。

## 子 Process と受け渡し

| 順 | Call Activity | 入力と供給元 | 出力と受け取り手 |
| --- | --- | --- | --- |
| 1 | [P0002-00001 版数付き変更を準備して commit する](P0002-00001.md) | 対象リポジトリ、作業ブランチ、既存の変更、版数とタグの規約、ビルド手順は親から受け取る。版数の更新指定と commit の依頼は利用者から受け取る。 | commit SHA を工程2へ。確認済みの版とタグの規約を工程4へ。ローカル ZIP の確認結果を利用者へ。 |
| 2 | [P0002-00002 Draft PR を公開する](P0002-00002.md) | commit SHA は工程1から、リポジトリ、作業ブランチ、変更の目的、リモート、base は親から受け取る。利用者の `miku-scm sync push` の依頼で開始する。 | PR の URL、公開ブランチ、head SHA、base を工程3へ。ローカルの `-done` ブランチを工程5へ。 |
| 3 | [P0002-00003 Draft PR を review して merge する](P0002-00003.md) | PR の URL、公開ブランチ、head SHA、base は工程2から受け取る。担当者は親から受け取る。 | 対象 PR と確認済みの merge commit SHA を工程4・5へ。 |
| 4 | [P0002-00004 GitHub Release を作成して公開する](P0002-00004.md) | 版とタグの規約は工程1から、対象 PR と merge commit SHA は工程3から、担当者は親から受け取る。 | タグ名と Release の公開結果を利用者へ。 |
| 5 | [P0002-00005 merge を検証して次の work branch を作る](P0002-00005.md) | `-done` ブランチ、公開ブランチ、head SHA、base は工程2から、対象 PR と照合用の merge commit SHA は工程3から、リポジトリは親から受け取る。利用者の `miku-scm sync pull` の依頼で開始する。 | マージの検証結果と次の作業ブランチを利用者へ。 |

利用者が示した操作順を、この例では5件の子 Process にまとめました。再利用時は、利用者が呼び出す Process と順序を指定します。順序の指定は工程の組み立てに使います。push と pull は、それぞれの実行依頼を受けた時点で開始します。

## 入出力と完了条件

この実例では Release 公開の後に `sync pull` を行いました。工程4と5は、どちらも工程3で対象 PR のマージ結果を得た後に開始できます。案件によっては、`sync pull` の後でタグを作成して Release を公開する順序も選べます。

親 Process は、Release 公開の結果と、PR のマージを照合して開始した次の作業ブランチの両方が揃った時点で完了します。Release ページや配布 ZIP も確認した場合は、その結果を添えます。
