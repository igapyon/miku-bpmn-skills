# P0002-00000 — miku-bpmn の GitHub Release

この親 Process は、[P00002 の作業記録と根拠表](../../process-mining/P00002/README.md)から組み立てた例です。

## 目的と入力

版数付きの変更を GitHub Release として公開し、PR のマージ後に次の作業ブランチを開始します。親 Process は対象リポジトリ、作業ブランチ、既存の変更とその目的、版数の更新指定と規約、配布 ZIP のビルド手順、リモート、base ブランチ、GitHub 上でレビューと公開を行う担当者を受け取ります。開始時に、今回使う版数更新の指定または合意済みの既定値と、利用者が依頼した実行範囲を確認します。前回の版数更新方法を既定値にする場合は、あらかじめ利用者と合意します。commit、push、完了報告後の pull は、開始時にそれぞれ指定することも、必要な時点で個別に依頼することもできます。

依頼例は「このリポジトリで P00002 を実行。版数は `a.b.c++`。`miku-scm git add commit`、次に `miku-scm sync push` を実行。GitHub 操作が完了したと報告したら `miku-scm sync pull` まで進めて」です。commit と push はそれぞれの依頼範囲を確認し、別の工程として順に実行します。

## GitHub 操作の案内

push は利用者から `miku-scm sync push` の依頼を受けて開始します。GitHub 操作の完了報告を合図に `miku-scm sync pull` まで実行するよう事前に依頼されていれば、報告後の照合に続けて pull します。事前の依頼がなければ、照合後に pull の依頼を待ちます。

Draft PR を作成したら、工程3と4の GitHub 操作を利用者の希望に合わせて案内します。案内方法は開始時にも途中でも指定できます。希望が分からない場合は一操作ずつ始め、必要に応じて手順一式を示せることを伝えます。

### GitHub 操作を一つずつ案内する

操作に慣れていないときや「一つずつ」と依頼されたときは、次に行う操作を一つだけ、できるだけ一行で伝えます。対象 PR やタグ名など、その操作に必要な情報を添えます。「Merge pull request」と「Confirm merge」のように一つの User Task に複数の操作が含まれる場合も、一操作ずつ示します。操作結果を受けてから次の指示に進みます。

### GitHub 操作を一度に案内する

操作に慣れていて手順一式を希望するときは、対象 PR の URL、マージ先、公開ブランチ、作成するタグ名を示し、残っている操作を順にまとめて案内します。最初から案内する場合は次の順です。

1. PR の差分とマージ先を確認し、問題がなければ **Ready for Review** にする。
2. **Merge pull request → Confirm merge** でマージする。
3. リポジトリの方針に従い、マージ済みの公開ブランチを **Delete branch** で削除するか、保持する。
4. **Draft a new release** で指定のタグを作り、この PR のマージコミットを対象として **Publish release** を実行する。

まとめて案内した場合は、すべて終えた時点で一度だけ完了を報告してもらいます。途中で止まった場合は、最後に完了した操作と止まった理由を報告してもらいます。

### 確認と再開

どちらの案内方法でも、AI は報告された完了済みの操作と User Task を記録します。案内方法を切り替える場合は、次の未完了の操作から続けます。すべての操作が終わったら、PR のマージとタグ・Release の公開を照合し、結果が一致したら事前の依頼に従って pull を実行します。照合結果が異なる場合は、該当する結果を示して停止します。

## 実行結果を記録し、途中から再開する

各子 Process の完了時と、人の操作や依頼を待つ時点で、完了済みの Task ID、対象リポジトリ・ブランチ・HEAD、その時点で得た出力、次の Task と待機条件を activity に記録します。人の操作を待つときは、案内方法と次の未完了の操作も記録します。Agent Skill を使った工程では、正式名、ワークフロー、渡した入力、結果も記録します。runner の記録があるときは run ID や operation ID を残し、対応する結果をたどれるようにします。

担当が替わる場合は、記録と現在の Git 状態、対応する runner の結果を照合し、最初の未完了 Task から再開します。push の結果が不明な場合は、保存済みの実行結果と公開状態を確認してから再開位置を決めます。

## 入出力と完了条件

この親 Process は Release 公開を確認してから `sync pull` を行う順序です。案件によっては、マージ後に先に `sync pull` を行い、その後でタグ作成と Release 公開を行うよう、親 Process の順序と受け渡しを変更できます。

親 Process は、Release 公開の結果と、PR のマージを照合して開始した次の作業ブランチの両方が揃った時点で完了します。配布 ZIP の添付も確認した場合は、その結果を添えます。
