# PM0001-00003 — 再利用できる候補を見つける

## プロンプト

根拠表から、他の仕事でも入力と完了を説明できる作業のまとまりを見つけてください。

- 1 の対象範囲と記録一覧 `{{scope}}`
- 2 の根拠表と出来事の前後関係 `{{evidence}}`

1. 目的、担当、成果物、作業の開始条件が変わる箇所を見て、Process を分ける位置を考えてください。前の工程の成果物を受け取って始められ、独自の成果物や完了条件を持つなら、別の候補にできます。同じ成果物をそろえるための細かな操作は、候補内のタスクにまとめます。一つの事例に基づく場合は、再利用できそうな理由を示してください。複数事例があれば、共通する工程と事例ごとの違いを示してください。
2. 候補ごとに `C01` のような ID を付け、目的、開始条件、入力とその提供者、タスクと担当、出力と受け取り手、完了条件を書いてください。タスクには `C01-T01` のような ID と対応する根拠 ID を付けます。入力がそろわないときに保留される作業が分かれば記してください。
3. 元の事例にあった固有名、作業先、規約、成果物などから、別の事例でも指定が必要な値を選び、入力や `{{変数名}}` にしてください。何でも変数にせず、候補を使う人が何を用意するか説明できる名前にします。元の値は具体例として示せます。
4. 人の判断が次の作業に必要な場合は、誰に何を聞き、回答をどこに反映し、どの作業がその回答を待つかを示してください。実績に現れた判断と、再利用しやすくするために設ける確認を見分けられるようにします。例えば、当時の通し確認が未実施でも、代表シナリオで試す工程を「追加案」として提案できます。
5. 確認できた順序と成果物の依存関係に沿ってタスクを並べてください。根拠から決められない必須の順序や分岐は確認事項とします。別の Process とつながる場合は「どの候補の出力が、どの候補の入力になるか」を示せます。親 Process の呼び出し順は、それを使う利用者が指定します。

### 出力

**Process 候補一覧**として、候補 ID ごとに次の項目を記してください。

- 目的、境界とその理由、開始条件、入力と提供者。
- タスク ID、作業・担当、前後関係と判断、根拠 ID。推定した工程には推定理由を、今後の工程として加えたいものには追加案と理由を添える。
- 出力と受け取り手、完了条件、他の候補との受け渡し、利用者に確認したい点。

候補に含めなかった重要な出来事があれば、根拠 ID とその理由を末尾に添えてください。
